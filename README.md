# Melissa는 무엇인가

> AI와 대화하며 하루를 돌아보고, 그 대화를 일기로 정리해 주는 AI 일기 앱

Melissa는 "일기는 쓰고 싶지만 막상 못 쓰게 되는" 문제를 풀기 위해 만든 Android 앱입니다.
사용자가 긴 글을 직접 쓰는 대신 AI와 친구처럼 대화하면, 앱이 그 대화를 바탕으로
제목, 주요 활동, 만족도, 다음 날 계획이 담긴 일기를 자동으로 생성해 날짜별로 저장합니다.

---

## 왜 만들었나

이 프로젝트는 **"기록"** 이라는 주제에서 출발했습니다.

기획 단계에서 또래(대학생·20~30대)를 대상으로 한 설문 자료를 살펴보니,
**일기 쓰기의 필요성은 느끼지만 정작 꾸준히 쓰는 사람은 많지 않다**는 점이 분명했습니다.
가장 큰 이유는 거창한 게 아니라 `"시간이 없다"`, `"귀찮다"` 였습니다.
즉, 동기가 없어서가 아니라 **기록이라는 행위 자체의 마찰(부담)** 때문에 멈추는 것이었습니다.

그래서 우리는 질문을 바꿨습니다.
"어떻게 더 좋은 일기 양식을 만들까?"가 아니라,
**"어떻게 하면 기록의 부담을 최소화하면서도 하루를 돌아보게 할 수 있을까?"** 였습니다.

여기서 떠올린 것이 **대화**입니다.
친구와 이야기를 나누다 보면 자연스럽게 그날의 감정이 풀리듯,
빈 화면에 글을 쓰는 대신 AI가 먼저 `"오늘 뭐 했어?"`, `"오늘 아쉬운 점이 뭐야?"` 하고
말을 걸어 주면 사용자는 답만 하면 됩니다.
대화가 끝나면 AI가 그 내용을 자동으로 요약·저장하고,
달력에서 지난 날짜를 누르면 그날의 일기와 대화를 다시 꺼내 볼 수 있습니다.

> **핵심 의도:** "쓰는 일기"를 "말하는 일기"로 바꿔, 기록의 부담을 낮추고
> 사용자가 자연스럽게 감정을 정리하며 하루를 되돌아보게 한다.

## 핵심 기능

| 기능 | 설명 |
| --- | --- |
| **대화형 하루 기록** | AI가 먼저 질문을 건네고, 답변을 바탕으로 대화를 이어갑니다. 같은 날에는 기존 대화를 이어서 쓸 수 있습니다. |
| **AI 일기 자동 생성** | 대화 내용을 GPT에 전달해 제목·주요 활동·감정·만족도(0~10)·다음 날 계획이 담긴 일기를 구조화된 형식으로 만들어 저장합니다. |
| **달력 기반 조회** | 월 단위 달력을 좌우로 넘기며 탐색하고, 기록이 있는 날짜에는 AI가 지은 일기 제목이 표시됩니다. 날짜를 누르면 일기와 당시 전체 대화를 볼 수 있습니다. |
| **"멜리사" 웨이크워드** | Picovoice Porcupine 한국어 모델로 메인 화면에서 "멜리사"를 감지하면 바로 채팅 화면으로 진입합니다. |

## 어려웠던 점 (해당 프로젝트를 통해 얻은 인사이트)

가장 많은 시간을 쏟은 것은 당시 베타였던 **OpenAI Assistants API v2를 Android에 통합**하는 작업이었고,
대부분의 어려움도 "AI를 쓰는 것"보다 **"AI를 하나의 상태 있는 시스템으로 다루는 것"** 에서 나왔습니다.

### 1. 비동기 상태 관리 — "응답은 한 번에 오지 않는다"

일반적인 요청·응답과 달리 Assistants API는 한 번의 답을 받기 위해
`Thread 생성 → Message 추가 → Run 실행 → Run 상태 Polling → Message 조회`의
여러 단계를 순서대로 관리해야 했습니다.
메시지를 보낸 직후엔 답이 없기 때문에 `threadId`와 `runId`를 유지하고,
Run이 `completed`가 될 때까지 1초 간격으로 상태를 반복 조회한 뒤에야 응답을 가져올 수 있었습니다.
콜백이 중첩되는 흐름 속에서 UI가 응답보다 먼저 갱신되거나 메시지가 누락되지 않도록
순서를 보장하는 설계가 가장 까다로웠습니다.

> **인사이트:** AI 기능도 결국 **명확한 상태 머신과 데이터 흐름**을 가진 소프트웨어다.
> 성공 경로뿐 아니라 실패·타임아웃·취소·재시도까지 흐름의 일부로 설계해야 한다.

### 2. 베타 API 직접 연동 — "참고할 예제가 없었다"

당시 Assistants API v2는 막 공개된 베타라 Java/Android에서 바로 쓸 예제가 거의 없었습니다.
그래서 공식 API 명세와 실제 JSON 응답을 직접 분석해
Retrofit 인터페이스(`GptApiService`)와 파싱 로직(`ChatMessage`의 `fromJsonResponse`)을 손으로 작성했습니다.

> **인사이트:** 새로운 API를 쓸 때는 SDK에 의존하기보다 **HTTP 규격과 상태 모델 자체를 이해**해야
> 막혔을 때 스스로 풀 수 있다.

### 3. 대화의 생명주기 정의 — "언제부터 새로운 하루인가"

앱을 다시 켜도 같은 날의 대화는 이어가되, 새로운 하루엔 새 대화를 시작해야 했습니다.
이를 위해 `SharedPreferences`에 Thread ID와 생성 시각을 저장하고,
**매일 오전 4시 30분을 기준**으로 Thread를 갱신하도록 구현했습니다.
"하루의 경계"라는, 코드에는 없던 개념을 직접 정의해야 했던 점이 흥미로웠습니다.

### 4. AI 결과를 앱 데이터로 연결 — "자유로운 출력은 저장하기 어렵다"

AI의 자유 형식 응답을 그대로 저장하면 달력과 상세 화면에서 일관되게 보여주기 어려웠습니다.
그래서 프롬프트로 출력을 `title`과 `summary`를 가진 **JSON으로 제한**하고,
본문은 HTML로 받아 SQLite 저장부터 화면 렌더링까지 하나로 연결했습니다.

> **인사이트:** 모델의 성능만큼이나 **출력 형식과 파싱 가능한 "계약"을 설계하는 일**이
> 제품의 안정성을 좌우한다.

### 5. 음성 기능의 Android 생명주기 처리

웨이크워드에는 마이크 권한뿐 아니라 Activity 상태에 따른 리소스 관리가 필요했습니다.
`onStart` / `onStop` / `onDestroy`에서 Porcupine의 시작·중지·해제를 각각 처리해
백그라운드에서 마이크를 점유하지 않도록 했습니다.

### 6. 외부 API 의존의 한계 — "시연 당일, 서버가 멈췄다"

가장 기억에 남는 순간은 발표 시연이었습니다.
웨이크워드("멜리사")로 앱을 띄우는 것까지는 완벽하게 동작했지만,
정작 핵심인 **대화 시연이 되지 않아** 미리 저장해 둔 기존 일기를 보여주는 데 그쳤습니다.
나중에 확인해 보니 그 시점에 **OpenAI API 서버가 신규 기능 배포로 인해 마비**된 상태였습니다.
내 코드의 문제가 아니라, **내가 통제할 수 없는 외부 의존성**이 제품의 핵심 경험을 그대로 멈춰 세운 것입니다.

> **인사이트:** 핵심 기능을 단일 외부 API에 전적으로 의존하면, 그 서비스의 장애가 곧 내 제품의 장애가 된다.
> 장기적으로는 타사 API에만 기대기보다 **자체(온프레미스) 모델·인프라로 핵심 경로를 통제**할 수 있어야
> 가용성을 스스로 보장할 수 있다. (최소한 장애 시 우아하게 대체·복구하는 설계가 필요하다.)

### 7. 구조를 직접 세운 경험 — "AI가 짜주지 않던 시절"

이 프로젝트는 ChatGPT가 막 등장한 초창기에 만들었습니다.
지금처럼 **디렉토리 구조나 코드베이스를 통째로 참고해 제품 뼈대를 잡아 주는 도구가 없던 때**라,
화면 흐름부터 패키지 구조, 계층 분리까지 종이에 직접 그려 가며 하나하나 세워야 했습니다.

번거로웠지만, 돌아보면 이 과정이 오히려 값진 경험이었습니다.
**구조를 스스로 고민하고 세워 본 경험**이 있었기에 각 계층이 왜 그 자리에 있는지 설명할 수 있었고,
이는 어떤 제품의 초기 프로토타입을 만들 때도 유지하고 싶은 습관이 되었습니다.

> **인사이트:** 도구가 구조를 대신 잡아 주는 시대일수록, **구조를 스스로 설계해 보는 습관**의 가치는 더 커진다.
> 초기 프로토타입이라도 "왜 이렇게 나눴는가"를 직접 고민해 본 사람만이 그 구조를 책임지고 발전시킬 수 있다.

## 기술 스택

| 구분 | 기술 |
| --- | --- |
| Language / Build | Java 8, Gradle 7.4 (AGP 7.3.0) |
| Android | AppCompat, Material Components, RecyclerView, ViewPager2, Fragment |
| Network | Retrofit2, OkHttp3, Gson |
| AI | OpenAI Assistants API v2, Chat Completions API |
| Voice | Picovoice Porcupine (한국어 모델) |
| Storage | SQLite, SharedPreferences |

### 동작 흐름

```text
웨이크워드("멜리사") 또는 버튼 → 채팅 화면 진입
        → Thread 조회/생성 → 사용자 Message 전송
        → Run 생성 → 상태 Polling → Assistant 응답 조회
        → (대화 종료 시) 요약 요청 → JSON + 전체 대화를 SQLite 저장
        → 달력에서 날짜별 일기 조회
```

저수준 API 호출을 앱에서 쓰기 쉽게 추상화하기 위해
`GptApiService`(엔드포인트) · `RetrofitClient`(인증/베타 헤더/타임아웃) ·
`ChatApiManager`(비동기 래퍼) · `ThreadManager`(Thread 생명주기) ·
`ChatActivity`(전체 오케스트레이션) 계층을 직접 구성했습니다.
배포용 범용 SDK는 아니지만, 여러 저수준 API를 조합한 **경량 Assistants API 래퍼**를 만든 경험입니다.

```text
app/src/main/java/com/example/melissa/
├── activities/   # 달력, 채팅, 일기 및 전체 대화 화면

├── network/      # OpenAI API 클라이언트
└── utils/        # Thread 및 FloatingActionButton 관리
```

## 실행 방법

**요구 환경:** Android Studio · JDK 17 · Android SDK 32

프로젝트 루트에 `local.properties`를 만들고 다음 값을 설정합니다.

```properties
sdk.dir=/path/to/Android/sdk
OPENAI_API_KEY=your_openai_api_key
PORCUPINE_ACCESS_KEY=your_picovoice_access_key
ASSISTANT_ID=your_openai_assistant_id
```

```bash
./gradlew testDebugUnitTest   # 단위 테스트
./gradlew assembleDebug       # 빌드
```

## 현재 한계와 개선 방향

이 저장소는 2024년에 만든 **학습용 프로토타입**으로, 현재 기준의 운영 환경을 목표로 하지는 않습니다.

- API 키가 `BuildConfig`를 통해 APK에 포함되므로, 실제 서비스에서는 백엔드 프록시가 필요합니다.
- Run의 실패·취소·만료 상태와 Polling 타임아웃 처리를 추가해야 합니다.
- API 실패 시 버튼·화면 상태를 복구하는 공통 오류 처리 구조가 필요합니다.
- 현재 테스트는 기본 예제 수준이라, 주요 사용자 흐름·API·DB에 대한 테스트가 필요합니다.
- SQLite 접근 계층을 통합하고 Room 등 구조화된 저장소로 전환할 수 있습니다.
- OpenAI Assistants API는 deprecated 상태이며 **2026년 8월 26일 종료 예정**입니다.
  계속 운영하려면 Responses API·Conversations API 기반으로 마이그레이션해야 합니다.

> 프로토타입을 완성한 뒤 가장 크게 배운 것은, **보안·테스트·오류 복구가
> "동작하는 프로토타입"과 "운영 가능한 제품" 사이의 가장 큰 차이**라는 점이었습니다.
